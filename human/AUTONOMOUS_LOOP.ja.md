# Codex自律研究ループ手順

この手順は、Codexに研究を一つの「作業」単位で自律実行させるためのものです。同じ目的の機械処理はまとめますが、人間の判断が必要な地点では必ず停止します。

「フェーズ」は計画、実装、実行、監査などの一段階です。`operation`は一ターンで完了させる作業単位で、関連するフェーズを最大三つ含みます。計画監査は、主指標だけを上げて研究目的を改善しない抜け道を実装前に調べる独立確認です。`ready`は自動実行可能、`blocked`は人間判断待ちを表します。

この通常モードは、計画承認などの人間判断を越えません。一件を途中確認なしで完了させる明示専用モードは`UNATTENDED_LOOP.ja.md`を参照してください。

## 起動方法

新しいCodexセッションで次を渡します。

```text
automation/AUTONOMOUS_LOOP_PROMPT.md に従って、研究ループを一作業だけ進めてください。
```

Codexは最初に次を実行します。

```bash
python scripts/next_autonomous_step.py
```

出力が`ready`なら、表示された`operation`を記憶してskillを実行します。終了後にルーターを再実行し、同じ`operation`の間だけ最大三フェーズまで続けます。`blocked`なら、表示された人間の承認、解釈、方針入力だけを求めます。

Agentを使うskillは、さらに`scripts/next_agent_action.py`で状態、承認、scope、hash、監査資料、保存済み出力を先に検査します。`build`は資料を機械生成、`compress`は同じ工程内で資料を圧縮、`accept`は完成済み出力を取込み、`blocked`は停止を意味します。圧縮は`$compress-audit-material`で処理して判定を再実行し、追加承認や別の監査を挟みません。Agentを起動するのは`delegate`の場合だけなので、中断後の再開で完成済み監査をやり直しません。

実験計画のレビューまたは実装へ進む前に、新規性確認も自動ゲートになります。最新の新規性確認が低または中リスクで、かつ進行可と記録されていない場合は停止します。高リスク、停止相当、人間判断が必要な場合も停止します。

## 進め方

1. `research/CONTEXT.md`で現在地を読む。
2. `research/STATE.json`の`next_action.mode`を確認する。
3. `scripts/next_autonomous_step.py`で、`operation`、使うskill、停止ゲートを確認する。
4. 表示されたskillで現在の一フェーズを進める。
5. 状態遷移、実行、監視、hash、context生成はscriptsに任せる。
6. 状態、証拠の内容、ゲートのアクションが進んだらルーターを再実行し、同じ`operation`なら最大三フェーズまで続ける。
7. `operation`が変わる、人間判断が要る、科学的・実行上の失敗がある、または修正しても進展がない時点で報告して停止する。書式だけの不備は`automation/PRESENTATION_REPAIR.md`に従って同じ工程内で修正する。

## 自動で進めてよい例

- `initial_setup`: 初期設定の未決項目を人間に確認する。
- `plan_experiment`: まだ修正可能な下書き状態（DRAFT）の実験計画を作る。
- `audit_experiment_plan`: 9,000文字以内の閉じた資料で計画の指標ハック可能性を独立監査する。
- `implement_experiment`: 承認済み計画だけを実装する。
- `review_implementation`: pilot/fullの実行前に`$audit-experiment-implementation`で閉じたbundleを独立監査する。
- `implemented`または`sanity_passed`: `$run-experiment`で決定的スクリプトを一回だけ実行する。
- `trained`: `$run-experiment`で中断したreview経路だけを復旧する。集約結果を再利用し、再学習しない。
- `review_required`: 未受理なら`$audit-experiment-integrity`、受理済み監査が`pass`または`warn`なら`$evaluate-experiment`を使う。
- `ready_to_finalize`: 必須項目と監査ゲートを確認して確定する。
- `debug_failure`: 失敗を一つだけ修正する。
- `maintain_memory`: 完了実験から知見、失敗、未解決問題、台帳を更新する。
- `update_direction`: 主張、提案手法、queue、停止判断を更新する。結果から新規仮説があれば、既存候補の有無によらず、根拠付きで最大一件をIDEA_BANKへ追加する。次に選ぶ比較は最大一件とする。
- `select_experiment`: 更新済みの候補一覧から次の実験を一つだけ作成する。

## 一つの作業にまとめる範囲

- `planning`（計画作業）: frontier/highで計画を固定し、新規性確認が未実施なら範囲を限定した確認を挟む。その後、別のfrontier/high Agent一つで計画監査まで行い、人間レビュー前で止める。
- `implementation_review`（実装確認作業）: 読み取り専用の実装監査を一回行い、`pass`または`warn`なら実行作業へ渡す。
- `result_review`（結果確認作業）: 完全性監査が`pass`または`warn`なら、評価と最終化まで続ける。
- `post_result`（実験後整理作業）: 記憶と証拠の更新、研究方向の更新、次の実験をDRAFTで一件作るところまで続ける。
- 実装、実行、失敗修正は互いに別の作業とし、一ターンでまたがない。

実装監査または完全性監査が`fail`なら直ちに停止し、次の作業を失敗修正にします。実験後整理でも、証拠と実験台帳の完了検査が通るまで次へ進みません。

計画作成または修正では、ロック後の計画監査まで同じ作業で行い、日本語レビューを表示して停止します。監査`fail`は修正、`warn`は人間による注意点の受入れが必要です。承認した次のターンでは承認記録と実装をまとめ、実験実行の前で停止します。

各フェーズのサブAgentは一つだけです。並列審査、自動再試行、暗黙のモデル切替は行いません。機械ゲートが返したAgentだけを使います。実装は計画で固定した`mechanical`、`balanced`、`frontier`を使い、再分類による昇格は別の明示的な計画修正後に最大一回です。

## 必ず停止する例

- 表示された計画について、承認、修正、延期の判断が必要な場合。
- 計画監査が`warn`または`fail`の場合。
- 新規性監査の結果が証拠不足、高リスク、棄却、または人間判断待ちの場合。計画監査前に確認がまだ一度も行われていない場合は、範囲を限定した新規性監査へ進みます。
- 結果解釈を人間が書く必要がある場合。
- fullの実行直前で対象IDへの学習承認がない場合。承認済み計画の実装・監査と、学習済み結果の処理は、この学習承認待ちでは止めません。
- 広い文献調査、全文読解、外部リポジトリ調査が必要な場合。
- 次が別の`operation`になる場合、または状態・証拠ファイル・ゲートのアクションのいずれにも進展がない場合。資料作成、監査、圧縮などでSTATEの工程名が変わらなくても、証拠やゲートが進めば継続します。

## 人間の役割

人間は、研究テーマ、新規性の最終判断、計画承認、結果解釈、広い調査許可、現在の研究枝または研究全体を打ち切る条件の変更だけを担当します。通常の状態遷移や実験実行はCodexとscriptsが行います。
