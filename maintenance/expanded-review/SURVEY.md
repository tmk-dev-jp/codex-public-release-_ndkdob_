The strongest candidates for local integration review are:

1. **Recoverable acceptance.** For the reported multi-file acceptance gap, prepare a bounded operation record containing request/response hashes, worker identity and intended file postconditions. On continuation, reuse that exact operation; accept each file only in its recorded before/after state, and reject conflicts. Test interruption after every write. A receipt written last alone does not resolve partial commits. G02/G11/P11 motivate this; they do not prove a particular local implementation correct.

2. **Evidence-bound result authority.** For the reported interpretation-source gap, reuse the existing dispatched-response proof checks rather than accepting an `agent` label. Test missing dispatch, foreign worker, changed response, stale inputs and unchanged files on rejection. G05/P05/P11 support provenance checks; authenticating evidence still does not establish its truth.

3. **Immutable evaluation during recovery.** Recovery must preserve the locked plan, machine facts, accepted audits, decision outcome and worker budget. Resume deterministic materialization, not scientific reasoning. G09/P09 and P03 support retaining numerical and integrity boundaries.

Competing approaches deserve explicit consideration. If existing gates already detect partial commits and offer a bounded manual recovery path, strengthening that detection may be enough. A single authoritative state file with atomic replacement is simpler when compatible with existing readers. SQLite can provide transactions, but migrating the repository is unnecessary unless current file contracts make a small recovery record inadequate. A generic workflow engine, reviewer panel, fresh replacement worker, or automatic retraining would expand scope without fixing the specific evidence boundary.

For external side effects, a persisted record alone cannot guarantee exactly-once execution. Official [AWS durable-execution guidance](https://docs.aws.amazon.com/durable-execution/patterns/best-practices/idempotency/) independently distinguishes replay, retries and idempotent effects. The proposed local work should claim only the acceptance/recovery properties its fault-injection tests actually demonstrate.
